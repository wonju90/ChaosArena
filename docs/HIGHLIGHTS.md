# ChaosArena 하이라이트

이 문서는 ChaosArena 프로젝트를 처음 훑어보는 사람이 가장 짧은 시간에 프로젝트의
핵심을 파악할 수 있도록 만든 요약이다. 두 부분으로 구성된다 — 이 프로젝트에서 가장
인상적인 장면인 **리전 페일오버 시나리오**를 글로 재구성한 워크스루, 그리고 지금까지
겪은 트러블슈팅 중 가장 서사가 좋은 것들을 추린 **하이라이트 아카이브**다.

더 깊이 들어가고 싶다면 다음 문서로 이어서 보면 된다.

- [ARCHITECTURE.md](../ARCHITECTURE.md) — 전체 구조와 시나리오 흐름
- [CONCEPTS.md](../CONCEPTS.md) — 왜 이런 설계를 택했는지
- [PROJECT_LOG.md](../PROJECT_LOG.md) — 트러블슈팅 38개 절 전문(증상→원인→해결)

## 1. 핵심 시나리오 워크스루 — 리전 강제 다운과 GSLB 페일오버

ChaosArena의 출발점은 `/` 게임 콘솔이다. Chaos 버튼(이지 모드)을 누르면 실행 중인
파드가 강제로 죽고, 몇 초 안에 쿠버네티스가 새 파드를 띄우는 과정이 화면에 그대로
드러난다. 복구가 끝나면 복구 시간에 따라 랭크(S/A/B/C)가 매겨진다. 쿠버네티스가
원래 하는 self-healing을, 죽이는 것부터 복구 시간 측정까지 게임처럼 체험할 수 있게
만든 것이 이 프로젝트의 한 줄 요약이다.

이 프로젝트의 목적은 기능 구현 자체가 아니라, 인프라를 직접 만들면서 실제로 부딪힌
문제를 어떻게 풀었는지 남기는 것이다. `PROJECT_LOG.md`에는 그렇게 남긴 트러블슈팅
기록이 38개 절 쌓여 있다. 관리형 쿠버네티스(NKS) 대신 `kubeadm`으로 클러스터를 직접
구축한 이유도 같은 맥락이다 — 더 배울 게 많기 때문이다([ARCHITECTURE.md](../ARCHITECTURE.md)
3.1절). 그리고 단일 클러스터가 아니라 KR1/KR2 두 리전과 GSLB로 구조를 넓힌 이유는,
Active 리전 자체가 통째로 죽는 상황까지 다루고 싶었기 때문이다.

`ARCHITECTURE.md` 0절의 다이어그램을 보면 전체 그림이 한 장에 들어온다 — 사용자 →
GSLB → KR1/KR2 각각의 Ingress → Pod, 그 옆에 Jenkins → NCR → ArgoCD → Pod로 이어지는
CI/CD 파이프라인, 그리고 Prometheus → Alertmanager → Slack으로 이어지는 모니터링
경로. 이 구조에서 가장 중요한 특징 하나는 **KR1과 KR2가 완전히 대칭 구조**라는
점이다. Jenkins/ArgoCD/모니터링이 양쪽 리전에 각각 다 존재한다. 그렇지 않으면 Active
리전이 죽었을 때 배포 자체를 할 수 없는 단일장애점(SPOF)이 생기기 때문이다. 이
대칭 구조는 처음부터 설계된 것이 아니라, 실제로 이 문제를 겪고 나서 컨트롤 플레인을
이중화하며 고친 결과다(PROJECT_LOG 4.34절).

이 아키텍처가 실제로 의미를 갖는 장면은 `/infra` 탭에서 벌어진다. 이 시나리오의
핵심은 **"리전 헬스체크"와 "GSLB 실제 전환"이 서로 다른 타임스케일로 움직인다는 것**을
눈으로 확인시켜주는 데 있다.

평소 `/infra` 탭에는 KR1이 Active로 표시되어 실제 트래픽을 받고 있다는 배지가 떠
있다. 이 상태에서 Active 리전(KR1)의 배포를 강제로 0으로 스케일 다운시키면, 몇 초
안에 `/infra` 화면의 KR1 카드가 빨갛게 바뀐다. 이건 ChaosArena 앱이 직접 반대편
리전에 연결해서 상태를 확인한 결과이기 때문에 이렇게 빠르다.

그런데 같은 화면 위쪽의 GSLB 배지는 이 시점에도 여전히 KR1을 가리킨다. 실제 사용자가
체감하는 DNS 전환은 TTL 30초 때문에 대략 30~80초가 걸린다. `/infra` 화면을 굳이 두
단으로 나눠둔 이유가 바로 이 차이 — 앱 레벨의 헬스체크(수 초)와 DNS 레벨의 GSLB
전환(수십 초)이 별개의 타임스케일이라는 것 — 를 드러내기 위해서다. 이 기다림의
시간 동안 CI/CD 탭에서 Jenkins → ArgoCD GitOps 흐름을 살펴보거나, 컨트롤 플레인
이중화 이야기를 더 들여다볼 수 있다.

기다림이 끝나면 GSLB 배지가 KR2로 넘어가고, 새로 생긴 페일오버 이력에 "KR1 → KR2"
한 줄과 함께 실시간으로 도는 지속시간 카운터가 나타난다. 실측으로는 보통 67~80초
구간에서 전환이 완료된다. 이후 KR1을 다시 복구시키면 카드가 초록으로 돌아오고,
failback도 같은 방식으로 자동 확인된다 — 이 failback 실측 기록은 PROJECT_LOG
4.15절에 남아 있다.

### 직접 재현해보고 싶다면

실제 환경에서 이 시나리오를 다시 재현해보고 싶다면 아래 명령으로 확인할 수 있다.
어느 리전이 현재 Active인지는 GSLB 우선순위 재조정 이력에 따라 그때그때 바뀔 수
있으므로, 먼저 `/infra`에서 실제 Active 리전을 확인한 뒤 그 리전의 마스터에서
실행해야 한다.

**Active 리전 마스터**에서 배포를 강제로 내린다.

```bash
kubectl scale deployment/chaos-demo --replicas=0
```

**같은 마스터**에서 복구한다.

```bash
kubectl scale deployment/chaos-demo --replicas=3
```

> **참고**: ArgoCD의 `selfHeal: true` 옵션이 켜져 있어서, `replicas=0`으로 내린
> 변경 자체를 ArgoCD가 "Git 상태와 다르다"고 판단해 스스로 3으로 되돌릴 수 있다.
> 복구 명령을 실행하기도 전에 파드 수가 저절로 돌아와 있다면, 그건 사람이 되돌린
> 것이 아니라 ArgoCD GitOps가 스스로 되돌린 것이다.

외부에서 실시간으로 지켜보는 별도 창을 하나 더 띄우고 싶다면 다음 스크립트를
사용할 수 있다.

```bash
./scripts/06-test-gslb-failover.sh http://www.<본인도메인> 3
```

## 2. 트러블슈팅 하이라이트

### 2.1 가장 추천하는 3가지

프로젝트 전체 히스토리(38개 절) 중에서 서사와 근본 원인 분석의 깊이 면에서 가장
추천할 만한 세 가지를 꼽으면 다음과 같다.

**Terraform이 운영 중인 서버를 통째로 재설치할 뻔한 사고를 사전에 막음** — `terraform
plan`에 뜬, 겉보기엔 별로 중요하지 않아 보이는 diff 하나를 그냥 넘기지 않고 클라우드
프로바이더의 소스 코드까지 읽어 들어갔다. 그 결과 이 diff를 그대로 apply했다면 이미
운영 중이던 살아있는 클러스터가 `Rebuild()`로 통째로 재설치될 뻔했다는 사실이
드러났다. 실제 피해가 발생하기 전에 근본 원인을 찾아 막은 사례다. (PROJECT_LOG.md
4.17절)

**파드끼리 네트워크가 안 되는 문제** — 클러스터 전체가 정상으로 보이는데도 파드 IP로
직접 curl을 날리면 타임아웃이 났다. 원인은 클라우드의 네트워크 보안 모델
(anti-spoofing)이 CNI(Calico)의 기본 설정과 충돌하는 데 있었다. 인프라의 각 레이어를
하나씩 검증해나가며 근본 원인을 좁혀낸 사례다. (PROJECT_LOG.md 4.8절)

**Slack 알림이 안 오는 문제** — 서로 무관해 보이는 원인 세 가지가 겹쳐 있었다.
Helm 플래그 하나가 예상과 다르게 동작하는 함정, 다른 네임스페이스에 놓인 Secret,
그리고 리소스 병합 동작이 의도치 않게 필요한 기본 설정을 조용히 지워버린 문제까지.
한 겹씩 벗겨내며 세 원인을 모두 찾아낸 사례다. (PROJECT_LOG.md 4.12절)

### 2.2 전체 아카이브

지금까지 프로젝트를 진행하며 겪은 문제 전체를 카테고리별로 정리한다. 각 항목 끝의
절 번호로 `PROJECT_LOG.md`에서 원문(증상→원인→해결 전문)을 바로 찾을 수 있다.
"★★★"는 서사의 임팩트를 주관적으로 매긴 것이다 — 반전이 있거나("겉보기 원인과 진짜
원인이 다르다"), 근본 원인까지 파고든 깊이가 있는 것 위주로 높게 매겼다.

#### A. 클라우드 인프라 기초 (Terraform / 네트워크 / 쿼터)

- **Keystone v3 인증 실패**(4.1) — 틀린 비밀번호를 넣어도 똑같은 에러가 뜨는 걸 보고
  "이 메시지 자체가 무의미하다"고 판단, 진짜 원인(v2.0 죽은 엔드포인트, v3는 user_id 인증)을
  찾은 사례. ★★
- **인터넷 게이트웨이 1:1 제약**(4.4) — Terraform provider에 게이트웨이 생성 리소스 자체가
  없어서, 새 VPC 대신 기존 VPC/서브넷을 재사용하도록 설계를 통째로 바꾼 사례. ★
- **Calico VXLANCrossSubnet vs OpenStack anti-spoofing**(4.8) — 파드 IP로 직접 curl해도
  타임아웃 나는 원인을, 클라우드 인프라 레벨부터 하나씩 검증해가며 "CNI와 클라우드의 네트워크
  보안 모델이 충돌"한다는 근본 원인까지 좁힌 사례. **온프레미스면 안 겪었을 문제가 클라우드
  라서 드러난** 좋은 소재. ★★★
- **KR1 Terraform state drift — `image_id` + boot-from-volume**(4.17) — `terraform plan`에
  뜬 이상한 diff 하나를 무시하지 않고 프로바이더 소스 코드까지 읽어서, 방치했다면 **운영 중인
  클러스터 전체가 재설치(`Rebuild()`)로 날아갈 뻔한** 잠재적 대형 사고를 사전에 막은 사례.
  "이상한 diff는 값 자체를 근거로 소스까지 내려가서 확인한다"는 원칙을 가장 잘 보여줌. ★★★

#### B. 쿠버네티스 스케줄링 / 배포

- **롤링업데이트 교착**(4.9) — replica 수 = 노드 수 + 강제 anti-affinity 조합이 기본
  롤링업데이트 전략(`maxSurge`)과 충돌해 배포가 멈춘 사례. "데모를 위한 설계(노드 분산 시각화)가
  배포 전략과 상성이 나빴다"는 트레이드오프 이야기. ★★
- **Jenkins CrashLoopBackOff — emptyDir 오염**(4.16) — StatefulSet 파드는 재시작해도 볼륨이
  그대로 유지된다는 성질 때문에, init 컨테이너가 "이전 실행의 흔적"에 걸려 넘어지는 자기
  반복적 크래시 루프에 빠진 사례. ★★
- **Jenkins 에이전트 영원히 "접속 대기"**(4.23) — 에러 메시지("포트를 바꾸라")를 액면 그대로
  따랐다가 K8s Service의 고정 포트 배선과 어긋나는 **새 문제를 만들어낸** 반전 있는 사례.
  "에러 메시지를 곧이곧대로 따르기 전에 그 값이 다른 곳에도 고정 배선돼 있는지 확인"이라는
  교훈. 레이어가 여러 겹이라 깊이감 있는 소재. ★★★

#### C. CI/CD 파이프라인 (Jenkins / NCR / cosign)

- **NCR 이미지 Pull 412 에러**(4.10) — 401/403이 아니라 412라는 HTTP 상태 코드 하나로
  "인증 문제가 아니라 정책(content-trust) 문제"임을 격리해낸 사례. ★★
- **cosign 서명 3중 장애물**(4.13) — referrers API 미호환(구버전 cosign으로 우회) →
  attestation이 이미지를 멀티 매니페스트로 만듦(`--provenance=false`) → `imagePullPolicy`
  기본값 때문에 캐시된 옛 이미지로 착각할 뻔한 것까지, 서로 무관해 보이는 장애물 3개를
  순서대로 격파한 사례. ★★★
- **Jenkins 첫 end-to-end 4중 장애물**(4.14) — Bitnami 태그 개편, non-root 컨테이너의 셸
  실행 실패, cosign 비밀번호를 로컬에서부터 재현해 원인을 좁힌 것, RBAC `watch` 누락까지
  — "파이프라인의 각 스테이지가 서로 다른 이유로 실패"하는 전형적인 CI/CD 디버깅 서사. ★★★
- **GitHub 웹훅 delivery 미재시도**(4.29) — "push했는데 배포가 안 됨"이 항상 코드 문제는
  아니라는 걸, 웹훅 delivery 로그로 확인한 사례(GitHub는 실패한 delivery를 자동 재시도 안 함). ★

#### D. 모니터링 / 알림

- **ServiceMonitor를 Prometheus가 인식 못 함**(4.11) — Helm 차트의 "합리적으로 보이는
  기본값"(`serviceMonitorSelectorNilUsesHelmValues`)이 숨겨놓은 함정을 문서까지 파고들어
  찾은 사례. 에러 로그조차 없어서(조용한 누락) 더 어려웠던 케이스. ★★
- **Alertmanager Slack 연동 3단 실패**(4.12) — `helm --reuse-values`가 `-f` 파일을 무시함 →
  Secret이 다른 네임스페이스에 있었음 → `receivers` 리스트를 통째로 덮어써서 `null` receiver가
  사라져 **Operator의 reconcile 전체가 실패**함, 이 세 레이어를 하나씩 벗겨가며 좁힌 사례.
  이 프로젝트에서 가장 계층이 깊은 디버깅 스토리 중 하나. ★★★

#### E. 멀티 리전 / GSLB

- **DNS Plus GSLB — Terraform 커버리지 밖의 콘솔 전용 기능**(4.15) — provider 스키마부터
  확인해 "이건 코드화 못 한다"고 판단하고, "DNS"와 "GSLB"가 콘솔에서 완전히 다른 탭이라는
  것까지 헤매며 알아낸 사례. 최종적으로 실측 80초 failover까지 검증. ★★
- **KR1 재구축 — in-place resize라 클러스터가 그대로 생존**(4.33) — RAM 쿼터가 풀려 정식
  스펙으로 재구축했는데, destroy 없는 in-place resize라 기존 kubeadm 클러스터가 그대로
  살아있어서 재작업을 상당 부분 피한, 사전에 `terraform plan`으로 예측해둔 덕을 본 사례. ★★
- **컨트롤 플레인 이중화 — 4가지 장애물**(4.34) — SPOF(KR2 죽으면 배포 자체 불가)를 없애려고
  KR1에도 Jenkins/ArgoCD/모니터링을 복제하면서 겪은 문제들. 대칭 아키텍처와 직접 연결됨. ★★

#### F. 대시보드 UI (가장 최근 작업)

- **ArgoCD 앱 트리 재현 — 권한 확장 없이**(4.36) — 새 RBAC 없이 `ownerReferences`만으로
  Deployment→ReplicaSet→Pod 계층을 복원한 사례. "최소 권한 원칙을 지키면서 기능을 추가한다"는
  이 프로젝트의 일관된 보안 기조를 보여줌. ★★
- **/infra UI 개편 — 장식이었던 상태 표시를 실제 헬스체크로**(4.37) — 대시보드에 Jenkins가
  "정상"으로 떠 있었는데 실제로는 파드가 죽어있었던 사건을 계기로, 색만 있던 상태 표시를 전부
  실제 HTTP 헬스체크로 바꾼 사례 — "장식적 UI가 거짓말을 하고 있었다"는 반전이 있어서 공감을
  사기 좋음. ★★★
- **GSLB Y자 커넥터 픽셀 디버깅**(4.38) — 사용자 피드백을 세 번 잘못 짚고 나서야(정렬 문제 →
  색상 대비 문제 → 진짜론 16px짜리 gap) 스크린샷을 픽셀 단위로 스캔해 정량적으로 검증한 사례.
  "느낌으로 고치지 말고 측정해서 검증한다"는 원칙을 가장 극적으로 보여줌. ★★★
